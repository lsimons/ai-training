In this lesson we give a coding agent the same small task twice. The first
brief is one sentence, and we watch which files the agent reads to make
sense of it. The second brief says where the task is and where it stops:
which files are in play, which are off limits, which function to imitate,
which test to extend and which command proves it done. Then we compare the
two sessions on the files they read and the diff they produce.

The brief is the agent's context, and the agent grounds its work in what it
reads, as [the retrieval lesson](/concepts/retrieval/) showed for a chat
model: an answer rests on the passage it was given, and the passage can be
the wrong one. A coding agent that picks its own files can pick the wrong
ones too. The vendor of Claude Code gives the same advice for its tool: say
which files are in play, what must not change, and which existing code the
new code should copy (@Claude Code best practices), and its short course
has a module on managing context (@Academy claude-code-101). Where this
lesson names a Claude Code feature it says so, and the source is checked on
the date shown above the lesson.

`done` is in nine of the ten files, so it narrows nothing. `undo` is in

agent that starts from a grep opens `legacy/todo_v1.py` and reads it with
the same attention as `todo.py`. The spec, the file that says what
`undo` should do, is the other hit, and the agent in the transcript didn't
open it.

**Scoping a task** is telling the agent where the task is and where it
stops: which module, which files are in play and which are off limits. It
has two effects you can see. The agent reads less, so more of its context
window is left for the work, and the vendor's own guidance names an
unscoped investigation that reads hundreds of files as a common failure
(@Claude Code best practices). And the change stays where you put it. A
well-meaning refactor of `done`, or a column in the CSV, is a change that
spreads because nothing told the agent to stop.

## Point at the file instead of describing it

The second half of the fix is **referencing files**: naming the exact file,
function or document the agent should read, so it loads the right context
on the first try. "The function that marks an item done" is a description,
and the agent has to search for what matches it, which is how it reached
`legacy/`. A path and a line range are an address, and there is only one
thing at an address.

<Predict id="run-reference" title="Read what the reference points at"
  answer={`16	def done(items, number):
  17	    index = number - 1
  18	    if index < 0 or index >= len(items):
  19	        return f"no item #{number}"
  20	    items[index]["done"] = True
  21	    return f"done #{number}: {items[index]['text']}"`} run="coding-with-agents/scoping-and-referencing/reference.py">
Print lines 16 to 21 of `todo.py` with their line numbers. This is what the
brief in the next section points at.

```sh
awk 'NR >= 16 && NR <= 21 { print NR "\t" $0 }' todo.py
```
</Predict>

That is the example to imitate. A brief that says "add `undo` next to
`done` in `todo.py` lines 16 to 21, with the same arguments and the same
checks" leaves the agent one thing to read and one pattern to follow. The vendor's guidance for
Claude Code says the same in its own words: point the agent at an existing
pattern in the codebase and name a file that is a good example of it
(@Claude Code best practices).

A brief most often needs the same references. The **example to imitate**
is the code the new code should look like, here `done` at `todo.py` lines
16 to 21. The **test to extend** is the test the new one should sit next
to, here `test_done_marks_the_numbered_item` at `test_todo.py` line 21.
The **spec to follow** is the document that says what the result should
do, here the `undo` row of `docs/SPEC.md`. Each one replaces a search with
a read.

In Claude Code, an `@` before a path in the prompt makes the agent read
that file before it responds, so `@todo.py` is a reference the tool acts on
as well as a hint to the model (@Claude Code best practices). In another
agent, write the path. The agent reads it, and a path it can open is exact where
a description it has to match is a guess.

<Pitfall title="The nearest plausible file">
An engineer asks an agent to "add an undo command, like the old one had".
The agent greps for `undo`, finds `undone` in `legacy/todo_v1.py`, and
builds the new command on that file: the old name, the old `reopened:`
message, and a `mark` helper the current `todo.py` doesn't have. The tests
pass, because nothing tests the message, and the spec that says
`open #<n>: <text>` was never read. The rule: when there is a file the
agent should imitate, name it, because otherwise the agent imitates the
first file that looks similar, and the first one is often the wrong one.
</Pitfall>

## Add what the code can't show, then run it again

What is left is what no file in the repository says. The task-level
boundary comes first: `store.py`, `render.py` and `export.py` are not part
of this change, and `legacy/` is never part of any change. The project's
instruction file, `AGENTS.md`, already contains the standing rule about
`legacy/`, which is where a boundary that holds for every task belongs
(@AEC-15). The boundary for this task goes in the brief. Then the check:
the command that says the task is done, here the test suite.

Reset the copy, start a fresh session, and hand over the scoped brief.

<Recap>
1. Scope a task by saying which files are in play and which are off limits. The agent reads less, and the change stays where you put it (@Claude Code best practices).
2. Reference files by path instead of describing them. Name the example to imitate, the test to extend and the spec to follow, or the agent imitates the first file that looks similar.
3. A boundary that holds for every task belongs in the project's instruction file, and the boundary for this task belongs in the brief (@AEC-15).
4. End the brief with the check that proves the task done, and run it yourself.
5. A scoped brief gives the reviewer a small diff, and a small diff is the one that gets read.
</Recap>
